# Existing controller operating plan

This guide proposes future operations; none of the mutating commands below ran during bootstrap.

For this internal implementation milestone, use the existing TaskScheduler through one controller entry point: the project virtual-environment Python with -m agrosphere_orchestrator.cli milestone execute AEO-6-ADJUDICATION. Do not create or repurpose an AutonomousRun. The original application's run is a different workflow with an expired immutable budget.

After administrator authorization, resolved execution-profile/handoff/legacy-operation gates, generated-plan review and authenticated plan approval:

1. milestone prepare AEO-6-ADJUDICATION produces exact pending execution UUIDs for currently eligible tasks. Repeated prepare reuses an outstanding AWAITING_APPROVAL request. It does not invoke a model.
2. milestone report AEO-6-ADJUDICATION and agent status --execution <actual UUID> display persisted plan/task/request evidence. tasks inspect <actual task UUID> and agents workload expose task state and outstanding claims. approvals pending only lists governance requests; scheduling-plan and execution-grant gates must also be inspected through milestone/agent reporting.
3. A configured authenticated HUMAN runs agent approve --execution <actual UUID> for each reviewed, bounded request. Separate inherited operation authorization remains required; the existing legacy actor API is not an authenticated substitute. Execute grants have expiry and are not blanket permission for later tasks.
4. milestone execute AEO-6-ADJUDICATION performs a finite drain of currently eligible, separately granted tasks. Dependencies need succeeded state AND task.verified evidence. It prepares the next wave and stops when fresh grants, missing artifacts, design/quality/security checks or uncertainty block it. No automatically approved task or repair is introduced. Candidate max_repairs=0 avoids automatic repair admission; any repair requires reviewed scope and a fresh exact grant.
5. After the next human decision, explicitly call the same milestone execute entry point again. It does not restart a run. milestone pause/resume control the same persisted plan; resume reconciles claims and clears pause, it does not itself execute. If an execution's process status is uncertain, use agent reconcile --execution <actual UUID>, inspect preserved reports/leases, and reconcile through milestone resume only when supported evidence proves termination. Never clear leases or replay writes directly in SQLite.

Persistence is the existing authoritative SQLite milestones/tasks, orchestration_plans/controls/evidence, executions/grants/attempts, claims/resource leases and append-only audit records. Model/validator outcomes, source HEAD/context digest, private worktree and preservation artifacts remain in .aeo/executions/<actual UUID>. Preserve branches, logs and artifacts on failure; do not clean an uncertain worktree or make a duplicate run. Existing import_plan rejects changed content under an existing milestone ID; propose_plan reuses an identical current historical revision. Changed options require a newly generated digest and fresh human plan review.

Authenticated commands already available (HUMAN only, when the corresponding actual persisted subject exists): milestone approve-requirements / approve-design / approve-delivery <milestone> support --reject; existing supplied requirements/design approvals must NOT be repeated. Governance requests use approvals inspect <request> then approvals decide <request> --decision approved|rejected --reason <exact rationale>, subject to that category's existing policy and governance SID list. Plan approval uses milestone approve-plan <milestone>. There is no supported authenticated plan-rejection flag or standalone execution-grant rejection command: withhold the grant/plan approval and use supported cancellation/pause/revision controls as appropriate; do not mislabel cancellation as authenticated rejection. The proposed evidence-specific CLI is part of the approved but unimplemented adjudication design and is not available today.

For the APPLICATION workflow, the existing AutonomousMilestoneController is exposed through autonomous resume <existing-run-id>, status/report/validate, and recover. It progresses between eligible steps, persists operation ownership/budgets/checkpoints, and stops with explicit AWAITING_APPROVAL/BLOCKED/RECOVERY_REQUIRED/PAUSED state. autonomous recover reconciles unfinished operations; it is not permission to repeat completed work. No application start/resume/recover command was invoked here. The protected original run ba0851d4-66bc-417a-851b-f08176bd8061 remains BLOCKED/RECONCILING/discovery-conflict with current_operation=null and its original expired deadline. Do not run resume merely because this internal plan is approved.

Approval-triggered continuation is MISSING: Windows verifier decisions append records but do not schedule a controller invocation. The approved architecture explicitly excludes a watchdog, new scheduler and automatic resume. If required later, govern a change to the existing continuation service: bind notification to the same run/milestone/current plan and decision digest, re-read all grants/dependencies/budgets and immutable deadline before admission, serialize operation ownership, make repeated notifications idempotent, preserve rejected/expired/uncertain states and never reset limits or create a new run. Review security and restart tests before implementation. This proposal grants no authority and changes no runtime.
